## 1. Project vision

- Official website of the Darbar Sharif

- Donation management (Mosque construction, Minaret construction, Lillah Boarding, General Fund)

## 3. Tech stack decision

**User's explicit instruction: keep the original spec — Next.js (frontend) + Laravel (backend API), MySQL database.** I (Claude) recommended collapsing to a single Laravel monolith (Blade + Livewire + Filament) for simpler hosting given the user is non-technical and self-hosting; the user declined and wants to keep the split Next.js + Laravel API architecture. Respect that decision unless the user revisits it.

- **Frontend:** Next.js (App Router), TypeScript, Tailwind CSS — public site + `/admin` panel UI, consuming the backend over REST.
- **Backend:** Laravel (PHP), MySQL in production. Use SQLite only for quick local checks if MySQL isn't available in-session — Laravel supports both via `.env` with no schema changes needed for most migrations (watch for MySQL-specific column types like `enum` if used).
- **Admin panel:** Laravel Filament is the user's own fallback suggestion ("Admin Panel: Laravel Filament (কাস্টমাইজড) অথবা Custom Admin") — but note Filament renders server-side Blade/Livewire admin pages, which sits oddly next to a separate Next.js frontend. Two reasonable options once unblocked:
  (a) Filament for `/admin` (separate PHP-rendered admin, reached at a subdomain or separate path on the Laravel app) while Next.js serves only the public site — simplest to build correctly with Filament's RBAC tooling.
  (b) Custom admin UI built in Next.js, calling Laravel API endpoints with Sanctum-based auth — matches the "one frontend codebase" feel but is considerably more build effort (every CRUD screen hand-built in React instead of generated by Filament).
  **Not yet decided — ask the user once backend work resumes**, leaning (a) for faster, more reliable delivery unless the user wants the exact same look-and-feel between public site and admin.
- **Auth:** Laravel Sanctum for API token auth (Next.js ↔ Laravel). RBAC via `spatie/laravel-permission`.
- **Two separate identity systems** (explicit project requirement):
  - `User` = CMS staff, needs Super Admin approval before login works.
  - `Member` = public visitor/donor account, instant self-serve signup, no approval needed.

## 4. Database schema

A complete first-draft schema already exists as a **Prisma schema** at `/backend/prisma/schema.prisma` in this repo — written before the Node-vs-Laravel pivot discussion. It is NOT meant to be used as-is (the project is on Laravel/MySQL per the decision above), but it is a complete, carefully thought-through **data model reference**: every table, field, relation, and status/enum convention needed for the full spec is already worked out there. When building Laravel migrations, port this schema's models 1:1 into Laravel migrations + Eloquent models rather than re-deriving them from scratch. Tables covered: User/Role/Permission/UserRole/RolePermission, Member, AuditLog, News/Comment/Reaction, Mahfil, DonationProject/Donation, Organization/OrganizationCommitteeMember, EducationPage/Teacher/Notice/RegisteredMadrasa, Book, Author/Article, TeamMember, GalleryAlbum/GalleryMedia, Banner, SiteSetting.

Note: that schema deliberately avoids Prisma's `enum` type (unsupported on SQLite) in favor of documented-string-convention fields — this constraint does NOT apply to Laravel/MySQL, so real Laravel migrations can use proper `enum` columns or a lookup table, whichever fits the team's taste.

## 5. Roles (RBAC)

User confirmed **5–8 real people** will actually use the admin panel (medium team), not the full 15-role list from the original master prompt. Practical role set to implement first, trimmed from the original spec:

1. **Super Admin** — full control, role/permission management, homepage control, settings, backup, logs
2. **News Editor** — News: create/edit/publish/SEO
3. **Mahfil Manager** — Mahfil: create/edit, banners, scheduling (incl. whole-year advance planning)
4. **Donation Manager** — Donation projects: progress updates, manual donation records, reports/export
5. **Education Manager** — Madrasa pages, Board content, Registered Madrasa directory, notices
6. **Organization Manager** — the 4 organization pages, committee members
7. **Publication/Media Manager** — books, gallery, media coverage
8. **Writer** — own articles only, cannot publish directly (Reviewer/Editor approves)

Permissions per role, independently configurable: **view, create, edit, delete, publish, approve, export, restore** (export/restore added on top of the user's original list — export matters for Donation Manager's reporting, restore matters once soft-deletes are used anywhere).

Comment/reaction moderation queue is required on News and Articles (plain public comments were flagged as a reputational risk for a religious institution) — comments default to `pending` status, a moderator (News Editor or a dedicated Comment Moderator) approves before they go live.

## 8. Things explicitly ruled out for v1

- Online payment gateway (bKash/Nagad/card) — manual donation recording only for now; gateway needs separate merchant-account paperwork the user hasn't started.
- PDF book downloads.
- Search bar on the homepage (only on News/Article/Publication listing pages).
- AI-generated fatwa/Q&A answers — any "ask a question" feature must route to a human alem for review, never an automated answer.
- Full bilingual (Bengali/English) coverage of every page — start with homepage/About/Donation in English for international donors; everything else stays Bengali-only for now.
